# dav1d の並列復号比較（PC）

同じ長 GOP の AV1 の同じ約 6 秒区間を、1 / 2 / 4 / 6 スレッドで復号する。
状態保存・復元を呼び出さず、まず並列化そのものの効果を調べる実験。
アプリ、既存の容量削減実験、チェックポイントの単一スレッド制約は変更しない。

## 方法

- dav1d 1.5.4、上流コミット `54706fc6bc0cdecab7e9593974a4039cc038fca7` に固定。
- 同じ実行ファイル・入力・通常復号設定を使い、フレーム省略は行わない。
- `max_frame_delay=1`（同時処理 1 フレーム）を維持した設定と、
  `max_frame_delay=0`（dav1d の自動値）を分けて測る。
  自動値は 2/4 スレッドで 2 フレーム、6 スレッドで 3 フレーム。
- Windows が列挙した先頭の使用可能な 6 物理コアから、それぞれ論理 CPU を 1 個選び、
  **この試験プロセスだけ**が使う共通の CPU 集合とする。
  全設定で同じ集合を使い、過去の「1 コア固定」は引き継がない。
- 各計測は新しい復号器で開始。先頭から約 14 秒までを時間外で復号し、
  保留中の出力・フレーム処理をすべて取り出してから、約 14〜20 秒の区間を計測する。
  前半の並列復号を区間タイマー外へ重ねて高速に見せる方法は使わない。
- 目的フレームが実際に `get_picture` から返った時刻までを測る。
  後続パケットを先に渡して目的位置の判定をずらさない。
- 取得済み RAM パケットのコピー・投入・通常の画像受け取りを含む。
  通信、音声、UI、物理画面表示、画像照合、初期化、前半 14 秒の復号は時間外。
- 全設定を順番を回しながら各 5 回実行し、生値と中央値を残す。

以前の単一フレーム用テスターは、各パケットの直後に出力を最後まで取り出す。
これを複数フレーム設定へそのまま流用すると、処理を直列化してしまう。
本実験では入力を渡すたびに受け取りを 1 回試し、次の入力を先に提供する。
繰り返しの drain は前半/計測区間の終端と入力の backpressure に限る。

## 正しさの確認

時間計測とは別のパスで、独立した 1 スレッド復号器と各並列設定の出力を照合する。
遅延によって各パケット直後の出力数が異なるため、短いキューで出力順を合わせ、
区間中の **すべての画像の全 Y/U/V 有効画素を行ごとに memcmp** する。
PTS・入力との対応・画素形式・画像数も一致させる。
目的画像の時刻は計測パスでも確認し、時間だけで成功扱いしない。

画像比較用キューは 32 枚で上限を設け、画像そのものをログや結果ファイルへ出さない。
`processCpuMs` は全スレッドのプロセス CPU 時間の差。
Windows の更新粒度による量子化があるため、短い合成素材の CPU 時間/実時間の比を
正確な利用コア数と解釈しない。主な速度指標は高精度時計の `targetMs`。

## 実行

Windows、Python、Git、FFmpeg、MSYS2 MinGW64 の GCC/Meson/Ninja/NASM を使う。

```powershell
python experiments/dav1d-parallel/run.py
python experiments/dav1d-parallel/run.py --input 'ローカルの長GOP-AV1.mkv'
```

合成 8bit / 10bit 素材を使い、`--input` を指定すると実ファイルでも同じ比較をする。
原本を変更せず、先頭 25 秒を codec copy で IVF に詰め替える。
実験対象の約 14〜20 秒にキーフレームをまたぐかは入力による。
今回の実ファイルは次のキーフレームが 22.289 秒で、測定区間は同じ GOP 内。

既存の PC 用ビルド `.local/dav1d-checkpoint` を再利用する。
状態保存コードもリンクされるが、今回の並列テストでは呼ばない。
ソース PIN・追加コードの SHA-256・使用ライブラリの SHA-256 を集計に残す。
画像データ、入力、生成物、生ログは `.local/`、公開する集計には入力名やパスを含めない。

## 結果の適用範囲

これは並列復号の速度と画像一致の確認であり、並列状態の保存・復元の成功ではない。
今のチェックポイントは単一スレッド/単一フレーム限定のまま。
採用するには複数フレームに対応した待機・参照画像・進捗状態等の扱いを実装し、
キーフレームを越えた後の反復復元と全画素一致を改めて確認する必要がある。
CPU 構成や命令セットが異なるため、PC の時間や倍率を iPhone へそのまま当てはめない。

## 実測（2026-10-25）

Intel Core i7-12700K / Windows x86_64。CPU 集合は `0x555`（1365）。
同じ 1440×1080 / 10bit の長 GOP 素材の 14.031〜20.037 秒（6.006 秒）。各 5 回の中央値。

| 復号スレッド設定 | 同時処理フレーム数 | 目的画像まで | 1スレッド比 |
|---:|---:|---:|---:|
| 1 | 1 | 500.75ms | 1.00倍 |
| 2 | 1 | 428.82ms | 1.17倍 |
| 4 | 1 | 425.86ms | 1.18倍 |
| 6 | 1 | 414.73ms | 1.21倍 |
| 2 | 2 | 303.46ms | 1.65倍 |
| 4 | 2 | 237.69ms | 2.11倍 |
| 6 | 3 | 180.25ms | 2.78倍 |

全 3 素材・各 7 設定で、計測区間の 145 枚すべてが単一スレッドの出力と全画素一致した。
実ファイルの 6 スレッド・3 フレーム設定では、プロセス CPU 時間/実時間の中央値も約 3.31 で、
単にスレッド数を指定しただけでなく実際の並列処理が観測できた。

同時処理を 1 フレームに制限したままの 6 スレッドは約 415ms。
スレッド数に加えてフレーム間の並列処理が大きく寄与した。
チェックポイント方式でこの速度が得られるかと、iPhone 上での効果はまだ未確認。
