# 10bit 参照画像の詰め込みによるチェックポイント容量削減

PC 限定の実験。アプリで使う既存の状態保存処理・ビルド設定は変更しない。
上流 dav1d 1.5.4 (`54706fc6bc0cdecab7e9593974a4039cc038fca7`) に対し、
既存の `../dav1d-checkpoint/checkpoint.c` を変更せずに使う。
追加コードのライセンスも BSD-2-Clause。
上流の著作権・条件は [COPYING.dav1d](../dav1d-checkpoint/COPYING.dav1d) を参照。

## 保存形式

10bit 画素の uint16 値を、4 画素＝5 bytes に詰める。8bit は比較用のそのままコピー。
画質を落とす量子化や動画の再エンコードは行わない。
画像の行の余白、画面外の行、平面間の隙間、アロケーター末尾の追加領域は
**元のバイト列をそのまま保存**する。これらが 10bit の値やゼロであるとは仮定しない。
画像外の復号参照を誤って変えないため、今回は余白の削減や再生成を行わない。
同一チェックポイント内の同じ画像は一度だけ格納する。

保存後は元の画像バッファと picture context の参照を外し、シーケンス/フレームヘッダー、
CDF、動きベクトル、セグメンテーション等を保持する。
単に小さなコピーを増やしつつ元画像も保持する実装ではない。
統計は元画像を保持する `ref` / `data` / `allocator_data` が残っていないことも確認する。

復元は同じ単一スレッド復号器に対して行う。通常の作業領域を再利用し、必要な画像を
既定アロケーターで再確保して展開する。参照スロットが同じ画像を共有する関係と、
各スロット固有のプロパティを復元する。追加の復号器を待機させる設計ではない。
内部の画像確保ヘルパーは `.local/` の実験用クローンだけの `picture.c` に追加する。

## 検証

- 詰め込みの行幅 1〜257 の往復一致と、1024 以上の不正な画素値の拒否。
- 保存直後の元画像と展開結果について、**アロケーターの画像 payload 全 byte** を比較。
  表示部分に加えて、余白・未使用領域も一致させる。
- 通常復号を継続しても保存処理の影響がないこと。
- 次の本物のキーフレームを通過してから元の地点へ戻す操作を 5 回繰り返し、
  各回の全 Y/U/V 有効画素、PTS、入力との対応、出力数が独立した通常復号器と一致すること。
- 繰り返し保存・解放、同じ復号器への復元、別の所有者への復元拒否、空の復号器の保存拒否。
- 所有する復号器を閉じてから保持状態を解放する処理。

素の参照保持と詰め込み方式は別のフェーズで動かす。
詰め込み方式のフェーズに、元画像を保持する比較用チェックポイントを残さない。
各フェーズの通常比較用の復号器はテスト用で、速度計測とは別に動かす。
全画素・画像全 byte の照合は速度計測に入れない。

## 時間と容量の定義

- `saveMs`: 既に復号された地点の保存。詰め込み・確保・メタデータ保持を含む。
- `restoreMs`: flush・画像確保・展開・参照の再設定を含む。目的位置までの復号は別。
- `restoreAndSuffixMs`: 復元開始から、目的位置の画像が得られるまで。
- `freeMs`: 同じ地点で作った一時状態を解放する時間。
- `heldBytes`: 保存状態の構造体・詰め込んだ画像の確保量・重複除去した保持メタデータ。
  CRT の確保管理費やプロセス全体の使用量ではない。

圧縮入力は取得済みの RAM データ。通信、音声、UI、物理画面への表示を計測に含めない。
Windows の最初の使用可能な論理 CPU に試験スレッドを固定し、同じ実行ファイル・
同じ dav1d で両方式を測る。各 5 回の生値・中央値を残す。
PC での絶対時間から iPhone の時間を予測しない。

保存時は詰め込み用のコピーが必要なので、素の参照共有より処理と一時メモリーが増える。
復元中・通常復号中は元の 16bit 形式の参照画像が必要。`heldBytes` が減った分だけ
プロセスの使用量がすぐ減るとは限らず、復号器の遊休プールや OS/CRT のキャッシュは別。
複数地点間の共有・総使用量・連続再生の負荷・先行復号の電力は今回の測定対象外。
HDR・マルチスレッド・12bit 等は未対応。確認素材は SDR の 4:2:0。

## 実行

Windows、Python、Git、FFmpeg、MSYS2 MinGW64 の GCC/Meson/Ninja/NASM を使用する。
リポジトリ直下で実行する。

```powershell
python experiments/dav1d-packed-checkpoint/run.py
python experiments/dav1d-packed-checkpoint/run.py --input 'ローカルの長GOP-AV1.mkv'
```

先頭 32 秒を codec copy で IVF に詰め替え、原本を変更しない。
合成素材は既存の 8bit / 10bit を使用し、保存位置 18 秒、目的位置 20 秒、照合終了 30 秒。
任意入力も先頭が実キーフレームで、20 秒より後から 30 秒までに次のキーフレームがあるものを使う。
任意入力では保存位置 19.8 / 18 / 14 秒を試す（実際は直後のパケット境界）。
全試験を通らない入力から速度改善を主張しない。

ソースのクローン、入力、生成物、生ログは `.local/`。
完成したケースから `.local/packed-checkpoint-results.json` へ集計を書き出す。
公開する集計には入力パス・録画名・画像・メディア payload を含めない。

## 実測結果（2026-10-25）

Intel Core i7-12700K / Windows x86_64、1 スレッド、論理 CPU のマスク 1 に固定。各 5 回の中央値。
同じ 1440×1080 / 10bit の長 GOP 素材を使用。保存地点は 3 箇所、目的位置は 20.037 秒。

| 目的位置までの距離 | 素の保持量 | 詰め込み保持量 | 詰め込み保存 | 展開を含む復元 | 素の復元＋復号 | 詰め込み復元＋復号 |
|---|---:|---:|---:|---:|---:|---:|
| 0.209秒 | 26.400MiB | 18.056MiB | 5.386ms | 3.590ms | 13.704ms | 17.073ms |
| 2.002秒 | 26.400MiB | 18.056MiB | 5.492ms | 3.622ms | 167.618ms | 168.951ms |
| 6.006秒 | 26.400MiB | 18.056MiB | 5.903ms | 3.642ms | 504.876ms | 518.707ms |

実ファイルの削減率は約 31.61%、1 地点あたり約 8.34MiB。保持する参照画像は 5 枚。
全 5 ケース（合成 8bit / 10bit と実ファイル 3 地点）に合格した。8bit の対照では画素を詰めず、
メタデータ/管理オブジェクトの差だけなので、大きな容量削減はない。
元の画像バッファ参照を残さず、画像領域全 byte と、その後の復号画像が一致した。

12〜15 地点で単純に合計すると約 216.67〜270.83MiB。地点間の共有や、復号作業領域、
復元時の一時領域、メモリー管理側の保持は別であり、アプリ全体の使用量を実測した数値ではない。

展開そのものは約 3.6ms だったが、6 秒先の目的画像を得るまでには約 519ms かかった。
保存地点から遠ければ、その間の復号は引き続き必要。各総所要時間の差にはキャッシュや
通常の実行変動も含まれるため、両中央値の差をそのまま純粋な展開時間と解釈しない。

GCC 16.2 により、変更していない上流 `ipred_tmpl.c` に配列境界の警告が出た。
追加コードへの警告はなかった。両方式はこの同じライブラリを使って比較した。
iPhone での時間・連続再生中の負荷・発熱・電力は未測定。アプリの実装/ビルドには未反映。
