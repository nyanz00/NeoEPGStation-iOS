# チェックポイントの可逆圧縮と依存フレーム再構築（PC）

アプリを変更せず、現在の約18MiBの保持状態を減らす2方式を独立したPC実験で比較した。
元の映像・パス・番組名は保存しない。元ファイルは変更しない。CPU測定であり、Metal/GPU性能は未測定。

## 入力・測定範囲

- 同じ内容の長GOP AV1と約6秒GOP AV1。いずれも1440×1080・10bit。実録画各3地点、合計6地点。
- 小さい320×180・10bitの合成素材を1地点。合計7ケース。
- dav1d 1.5.4固定リビジョン、6ワーカー・3フレーム、6物理コアの同じaffinity。
- 入力は事前にRAMへ取得。音声・通信・UI・画面表示を含めない。画像比較を各タイマーの外に置く。
- 圧縮は各方式3回。保存には状態確保・前処理・圧縮・保持データの作成を含む。復元には画像確保・展開・参照再設定を含む。
- 複数の保存地点を常時生成する際の再生負荷・フレーム落ち・発熱・電力は未測定。
- CPU版の速度をiPhone/GPUの速度へ換算しない。保存処理は単一呼び出しスレッドで、復号ワーカーは待機させる。

## 1. 可逆圧縮

表示用RGBに変換せず、実際の参照画像5枚の画素バッファを使用。復号状態・管理情報も保持容量へ含める。
参照画像の元バッファへの参照は外す。余白を含むallocation全バイトの往復一致を各方式3回確認し、
復元した状態から次の本物のキーフレームを越える後続映像も独立した通常復号器と全画素比較する。

下表の容量は実録画6地点の範囲と中央値、時間は地点ごとの中央値をまとめたもの。単位はMiBとms。

| 方式 | 保持量の範囲 | 保持量中央値 | 保存時間の範囲 | 復元時間の範囲 |
| --- | ---: | ---: | ---: | ---: |
| 現在の10bit詰め込み | 18.06〜18.06 | 18.06 | 5.73〜6.37 | 6.48〜7.74 |
| 生画素＋LZ4 | 5.86〜15.81 | 11.27 | 33.06〜50.36 | 9.99〜10.90 |
| 10bit詰め込み＋LZ4 | 5.04〜12.74 | 10.05 | 24.89〜31.38 | 13.47〜15.22 |
| 横方向差分＋LZ4 | 5.86〜15.11 | 10.16 | 41.87〜80.81 | 14.41〜16.90 |
| 差分・バイト整形＋LZ4 | 4.70〜10.74 | 7.43 | 38.25〜58.37 | 13.08〜15.48 |
| 生画素＋Zstd 1 | 4.04〜11.75 | 8.08 | 38.11〜65.65 | 16.78〜24.88 |
| 10bit詰め込み＋Zstd 1 | 4.06〜11.75 | 9.08 | 30.56〜40.69 | 20.72〜24.65 |
| 差分・バイト整形＋Zstd 1 | 3.14〜8.10 | 5.14 | 46.81〜67.45 | 20.57〜22.59 |
| 32画素ブロック最小値＋ビット詰め | 9.21〜14.80 | 12.50 | 19.14〜20.81 | 13.74〜16.95 |

差分は行ごとの左画素との差をzigzag符号化し、16bit残差の下位/上位バイトを行内で分離してから圧縮。
これは一般のbitshuffle全体ではない。LZ4はv1.10.0の固定ソース、Zstandardは1.5.7のレベル1。
ブロック方式は行ごと32画素の最小値・必要ビット幅・差分を保存する単独で展開可能な形式。
GPUで実装しやすい計算構造の比較候補であり、この実験はCPUの素朴な実装。GPU用に最適化したものではない。

有効画素以外の余白も破棄せず保存した。保持量は論理的に所有するデータ量で、作業領域や元画像との一時共存、
アロケーターのプールなどを含むプロセス全体のピークではない。

## 2. 元の圧縮フレームを選んで保持

通常復号中に実フレームヘッダーの参照スロット・更新先・primary referenceを記録する。
保存地点の全8スロット（重複除去で5画像）を起点に依存関係をたどり、必要候補となる符号化フレームを選択。
選択したフレームの圧縮ペイロードはそのまま保存し、除外したフレームはヘッダーだけ残す。
ヘッダーだけのFRAME OBUはこの実験専用のスタブで、標準AV1プレイヤーへ渡せる動画や本物のキーフレームではない。
専用のdav1d経路が不要な画像の復号を省き、ヘッダーによるスロット更新を再現する。
参照画像の画素だけでなくCDF・動きベクトル・セグメンテーション等も、必要なフレームの再復号によって再構成する。

元のトレースを解放してから、新しい復号器へ抽出済みの圧縮データとヘッダーだけを与える。
元の復号済み画像や保存状態を再構築へ注入していない。元の通常復号器は検証用の正解にだけ使用する。
再構築後は全参照スロットの有効Y/U/V画素を照合し、後続区間・目的画像の全画素一致も確認する。

重要な制限：現在はヘッダーで宣言された全7画像参照を安全側に含む。ブロックごとに本当に画素を読んだ参照だけを
追う最小グラフではない。未使用の参照候補をさらに絞る余地は未評価であり、今回の再構築時間を理論的な下限とはしない。

| 入力 | 保存地点 | 抽出データ等の保持量 | 選んだ符号化フレーム数 | 再構築時間 | キーから同地点まで |
| --- | ---: | ---: | ---: | ---: | ---: |
| 長GOP | 14.031秒 | 1.99MiB | 203 | 316.8ms | 470.7ms |
| 長GOP | 18.035秒 | 2.84MiB | 251 | 385.6ms | 531.6ms |
| 長GOP | 19.828秒 | 3.31MiB | 272 | 441.9ms | 596.2ms |
| 約6秒GOP | 12.279秒 | 0.95MiB | 37 | 94.7ms | 113.6ms |
| 約6秒GOP | 30.297秒 | 1.42MiB | 37 | 156.3ms | 179.7ms |
| 約6秒GOP | 60.327秒 | 0.57MiB | 37 | 74.4ms | 97.1ms |

符号化フレーム数には非表示の参照フレームも含むため、表示fpsから数えた枚数とは異なる。
JSONのoriginalCodedFramesは動画先頭から保存地点までの全符号化フレーム数。特に約6秒GOPの後半ケースでは
過去のGOPも数えるので、selected/originalをそのまま「現在のGOPの削減率」と解釈しない。
比較用のkeyToCheckpointMs/keyToTargetMsは、動画先頭ではなく直前の本物のキーフレームから測った公平な基準。
再構築レシピには過去の省略フレームの小さなヘッダーも含めるため、これを更に切り詰める最適化はしていない。

再構築と残り復号はタイマーを分け、間の全参照画素照合を計測から除外して加算する。
packedRestoreAndTargetMsは現在方式の比較値であり、可逆圧縮9方式の全シーク時間を全て測ったものではない。
レシピ作成の所要時間や長時間再生中の記録負荷は未計測。フレーム保持と再構築が成立するかのPC試作である。

## 結論と次の判断

可逆圧縮は、今回の実録画で約18.1MiBを3.1〜8.1MiBまで削減できた。容量だけでなく保存側のCPU時間も増えた。
まずはこの削減率と保存処理量を基準に、GPU向け処理・CPU SIMD最適化・実機での同時再生負荷を比較する価値がある。
圧縮フレームの依存集合は0.57〜3.31MiBまで小さいが、現試作では再構築に74〜442ms必要。
最小グラフでの更なる短縮は否定できないが、現時点の実測では可逆圧縮で画像を保持する方が復元は速い。

## 再実行

```powershell
python experiments/dav1d-checkpoint-storage/run.py --quick --report .local/storage-quick.json
python experiments/dav1d-checkpoint-storage/run.py --long-input "長GOPのAV1.mkv" --short-input "約6秒GOPのAV1.mkv"
```

Windows/Python/FFmpeg/MSYS2 MinGW64のGCC・Meson・Ninja・NASM・Zstd開発ライブラリを使用。
先行実験で準備した`.local/dav1d-mt`の固定リビジョンを別の`.local/dav1d-storage`へcloneし、
実験用フックだけを適用する。既存の実験・アプリのdav1dは変更しない。LZ4ソースは公式v1.10.0から取得しSHAを記録する。
ソース・ライブラリーのハッシュと全生値はresults.json、検査の集計はverification.json。通常のiOSアプリ、IPA、Actionsの変更はない。
