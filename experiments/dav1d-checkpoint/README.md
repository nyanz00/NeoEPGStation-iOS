# dav1d の復号状態を保持する PC 実験

長い GOP の AV1 について、復号済みの途中地点を保持し、キーフレームからのやり直しを省けるかを調べる独立した実験。iOS アプリ・AetherEngine・VLC・サーバー・録画ファイルは変更しない。

## 実装

アプリの依存ビルドと同じ dav1d 1.5.4、上流コミット `54706fc6bc0cdecab7e9593974a4039cc038fca7` を使用する。追加するファイルは `checkpoint.c` と `neo_checkpoint.h` のみで、上流の構造体レイアウトは変更しない。

パケットを処理し、出力を EAGAIN まで取り出した境界で以下を保持する。

- シーケンスヘッダーと 8 個の参照スロットの画像・フレームヘッダー
- セグメンテーションマップ、動きベクトル、参照時刻、CDF
- 操作点・フラグ等の継続に必要な小さな値

参照カウントで既存のバッファを保持するため、保存時に画像全体をコピーしない。その後も通常の復号を進め、戻るときは **同じデコーダー** の現在の状態を flush して保持した参照を戻す。保存位置以降の圧縮パケットだけを投入する。キーフレームやそれ以前のパケットを再投入しない。デコーダーを地点ごとに起動・待機させる実装ではない。

これはプロセス内の保持であり、ファイルにシリアライズできるチェックポイントではない。小さな状態構造体だけでなく、復号済みの参照画像が必要になる。

## 成功条件と試験

`probe.c` は別の通常復号器を照合用に使い、全 Y/U/V の有効画素を各行 `memcmp` する。タイムスタンプや画像の一部だけの一致では合格にしない。

1. 保存した状態を保持したまま通常復号を継続しても出力が変わらない。
2. 保存地点の後の本物のキーフレームを越えて進み、元の保存地点へ復元する操作を 5 回繰り返し、各回の全画素・出力数・入力との対応が一致する。
3. 状態がない空の復号器で同じ非キーフレームパケットから再開しようとすると、エラーまたは映像なしになる。
4. シーケンス未取得での保存、別のデコーダーへの復元は拒否する。
5. 所有するデコーダーを閉じた後でも、保持状態を解放できる。

試験範囲は 8bit/10bit の合成動画と、1440×1080 / 10bit / VFR の長 GOP 動画。保存地点は約 18 秒、目的位置は約 20 秒。実ファイルは約 19.8 秒で保存する場合も測る。照合は約 30 秒まで行い、途中のキーフレーム通過を実際の出力ヘッダーで確認する。

## 再実行

Windows、Python、FFmpeg、Git、MSYS2 の MinGW64 GCC/Meson/Ninja/NASM が必要。リポジトリ直下から実行する。

```powershell
python experiments/dav1d-checkpoint/run.py
python experiments/dav1d-checkpoint/run.py --input '任意のローカル長GOP-AV1.mkv'
```

`--toolchain` と `--ffmpeg` でツールの場所を指定できる。`--input` の試験では、先頭がキーフレーム、保存地点が非キーフレーム、目的位置より後から 30 秒までの間に次のキーフレームがある動画を使う。合わない動画では試験が失敗する。任意の動画に合わせて自動的に測定区間を選ぶツールではない。

先頭 32 秒の映像を **codec copy** で IVF に詰め替える。再エンコードしない。原本に書き込まない。IVF は入力パケットと時刻を取り出すためだけに使用する。合成素材は既存の `tests/fixtures/av1-seek-{8,10}.mkv`。上流ソース・生成物・入力パケット・生ログは `.local/` に置く。集計は `.local/checkpoint-results.json` に保存し、入力名・パス・動画内容を含めない。

GCC の Unicode 一時パス問題を避けるため、このスクリプトの子プロセスだけ ASCII の TMP を使い、コンパイラーへ渡すリポジトリ内パスは相対指定する。ユーザーの環境変数を永続変更しない。

## 測定の読み方

`results.json` は PC での集計結果。5 回の生値と中央値を残す。

- `fromKeyframeMs`: 新しい復号器で先頭の本物のキーフレームから目的画像まで。open 自体は計測外。
- `warmFromKeyframeMs`: 使用中の同じ復号器を flush し、再利用できるワークスペースを残して、先頭から目的画像まで。
- `restoreAndSuffixMs`: 同じ復号器に状態を戻し、残りの短い区間を復号して目的画像を得るまで。
- `saveMs` / `restoreMs`: 参照の保持・再設定だけの時間。保存までの通常の復号は含まない。
- `retainedBytes`: 保持した参照が生存させる、重複を除いたプールブロックと状態構造体。プールのヘッダーを含み、CRT の管理費、遊休プール、通常の復号作業領域、圧縮入力、試験照合用復号器のメモリーは含まない。

保存時点では画像を共有しているため、`retainedBytes` 全量をその場で追加確保するわけではない。通常の参照が入れ替わった後も保存用の画像が残る。複数地点で共有できる部分・独立する部分があるので、1 地点分から総メモリーの厳密値は求められない。

入力は RAM に取得済み。計測には入力パケットのコピーと画像の受け取り・解放を含むが、通信、音声、UI、物理画面への表示、タイミング中の画素照合は含まない。単一スレッドの PC 実測であり、iPhone の速度や現在のアプリのシーク時間との直接比較には使わない。

## 未対応・次の判断

- 単一スレッド、フレーム遅延 1、既定の画像アロケーター、SDR の限られた素材だけで確認した。HDR メタデータがある境界、途中の入力、未処理出力は拒否する。
- マルチスレッド、任意の AV1 機能・シーケンス変更、複数地点の競合、iOS のライフサイクル・メモリー圧迫は未検証。
- 所有する復号器を閉じた後は復元しない。保存物の解放のみ許可する。並行呼び出しは禁止。
- 状態を保存できるのは **dav1d で復号した地点**。VideoToolbox の内部状態を取り出す実装ではない。通常再生も dav1d にするか、別途チェックポイントを作る復号コストが必要。
- 保存地点より前や未取得の位置へは、通常のキーフレームからの復号が必要。実用化では地点数と保持メモリーを制限し、足りなければ通常シークに戻す設計が必要。

PC の試験は仕組みの成立確認まで。アプリ採用の判断には iPhone での復元速度・持続再生の CPU/発熱/電力・メモリー使用量を別途確認する必要がある。

## 今回の PC 実測（2026-10-25）

Intel Core i7-12700K / Windows x86_64。時間は最終測定 5 回の中央値。PC の CPU 配置・負荷を固定していないため、絶対値は測定回によって変動する。目的位置は約 20 秒。通常経路も同じ復号器のワークスペースを再利用する条件。

| 素材 | 保存位置 | 先頭キーフレームから | 状態復元＋残りの復号 | 保持データ |
|---|---:|---:|---:|---:|
| 合成 320×180 / 8bit | 18.021秒 | 95.54ms | 9.65ms | 1.30MiB |
| 合成 320×180 / 10bit | 18.021秒 | 92.00ms | 9.42ms | 2.43MiB |
| 長GOP 1440×1080 / 10bit | 18.035秒 | 3069.15ms | 321.85ms | 26.40MiB |
| 長GOP 1440×1080 / 10bit | 19.828秒 | 3075.55ms | 24.16ms | 26.40MiB |

全 4 ケースが全画素一致・5 回の再復元に合格。実ファイルは 22.289 秒のキーフレームを通過してから保存位置へ戻した。1 地点の保存構造体は 2,792 bytes、参照の再設定だけは中央値約 0.004〜0.008ms。残りの区間の復号はこの時間とは別に必要。

近くの状態を保持すれば長 GOP の先頭から再復号せずに済むことを確認できた。ただし、これは iPhone での再生・音声同期・表示までのシーク時間を測った結果ではない。
