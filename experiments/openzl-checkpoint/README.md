# OpenZL CPUによる参照画像の圧縮比較（PC）

## 結果

OpenZL 0.3.0の標準グラフ、数値グラフ、独自LZグラフを、既存のZstandard 1.5.7と比較した。
今回の参照画像では、単純な置き換えで圧縮速度と容量の両方が改善する結果にはならなかった。
独自LZはCPUのSIMDを有効にすると復元が速くなり、小さな速度・容量の交換条件が確認できた。

下表はCPU最適化あり（両ライブラリとハーネスに `-O3 -march=native`）の結果。
各地点でウォームアップ1回と測定5回を実行し、各地点の中央値を6地点で集計した中央値。
時間は参照画像5枚の圧縮・復元であり、シーク全体やデコーダーへの状態再設定は含まない。

| 方式 | 画像の保持量 MiB | 管理情報込み推定 MiB | 圧縮 ms | 復元 ms |
| --- | ---: | ---: | ---: | ---: |
| 生画素＋Zstd 1 | 7.346 | 8.082 | 48.25 | 22.73 |
| 既存の行差分・バイト整形＋Zstd 1 | 4.404 | 5.139 | 54.12 | 21.70 |
| OpenZL汎用 1 | 7.346 | 8.082 | 52.57 | 24.45 |
| OpenZL汎用 6 | 6.066 | 6.801 | 215.97 | 20.87 |
| OpenZL 16bit数値 1 | 6.723 | 7.459 | 111.47 | 35.44 |
| OpenZL 16bit数値 6 | 5.532 | 6.268 | 478.18 | 24.16 |
| OpenZL数値差分・zigzag 1 | 5.356 | 6.092 | 128.32 | 52.66 |
| OpenZL数値差分・zigzag 6 | 4.556 | 5.292 | 404.34 | 34.26 |
| 既存前処理＋OpenZL汎用 1 | 4.404 | 5.140 | 57.22 | 23.04 |
| OpenZL独自LZ 1 | 7.520 | 8.255 | 56.08 | 17.30 |
| OpenZL独自LZ 6 | 6.156 | 6.892 | 250.23 | 15.92 |
| 既存前処理＋OpenZL独自LZ 1 | 4.553 | 5.288 | 60.70 | 19.41 |
| 既存前処理＋OpenZL独自LZ 6 | 4.327 | 5.063 | 190.80 | 18.68 |

- 既存前処理＋独自LZ 1は既存Zstdに対して、画像容量が約3.4%増え、圧縮が約6.6ms遅く、復元が約2.3ms速い。
- 同LZ 6は画像容量が約1.7%減るが、圧縮時間が約3.5倍になる。管理情報込みの削減率は約1.5%。
- 数値グラフや1次元差分グラフは、今回の行単位の画像前処理を超えなかった。
- 汎用グラフは内部でZstdを選んでいた。固定ソースの `src/openzl/compress/selectors/selector_genericLZ.c`
  が `ZL_GRAPH_ZSTD` を返すことを確認した。独自LZは `ZL_GRAPH_LZ` を明示して別に測定した。
- CPU最適化なしで独自LZの復元が遅かったため、PCのSIMDを有効にした比較を追加した。
  iPhoneのNEONとは別であり、PCの時間をiPhoneへ換算しない。

## 入力と検証

- 1440×1080、10bit、YUV420の実録画。長GOPと約6秒GOPの各3地点、計6地点。
- 既存の固定dav1d 1.5.4の6ワーカー復号器を完全にdrainした境界で、実際の参照スロットを確認。
  8スロットの共有を除くと各地点5画像、画像allocationの合計は約25.66MiB。
- 表示用RGBや単なる出力フレームではなく、参照画像のallocation全体を使用。
  有効画素のほか、行余白・画像間余白・末尾も省かず、全方式に同じバイト列を渡した。
- 数値グラフはallocation全体を連続したlittle-endian 16bit配列として渡す。
  差分・zigzagグラフもこの1次元配列に適用する。画像専用の2次元予測器や訓練済みグラフではない。
- 既存前処理は行ごとの左画素差分、zigzag、行内の上下バイト分離。逆処理も測定に含める。
- 各方式は1圧縮スレッド、同じ論理CPU（affinity 1）。入力は事前にRAMへ取得。
  ファイルI/O・比較処理はタイマーの外。圧縮器のコンテキスト作成・前処理・出力確保と縮小は時間に含む。
- 全936組の実参照画像セット、画像単位では4,680回、allocation全バイトの完全一致を確認。
  さらにゼロ・10bit最大値・乱数・段階値と非ゼロの余白、奇数高さを持つ52条件・208画像で一致。
- これは画像圧縮の比較。新形式をデコーダーへ再注入した後続フレーム試験、音声・コメント描画との
  同時実行、長時間の発熱・消費電力、iOS実機試験は行っていない。通常再生とアプリは変更していない。

## メモリーの意味

GNU ldのmalloc/calloc/realloc/freeラッパーで、静的ライブラリとハーネスの要求量を追跡した。
各圧縮・復元の終了後、圧縮結果と元画像以外の新しい保持がないことを全回で確認した。
入力・標準入出力初期化の過程で残る115〜121バイトは事前baselineとして別記し、圧縮器のリークと混同しない。

`compressionAdditionalPeakBytes` は元画像の常駐量を除いた要求量のピークで、
前処理・出力バッファー・既にできた他画像の圧縮結果・ライブラリ作業領域を含む。
**純粋な圧縮器だけの作業領域ではない。** 安全側の出力容量としてOpenZLは元画像の2倍＋64KiB、
Zstdは公式compressBoundを用いたため、この値で両圧縮器の内部メモリーだけを直接比較しない。
この試作では既存Zstdが最大約16.7MiB、前処理＋独自LZ 1が約37.1MiB、数値差分グラフ6が約140.1MiB。
アロケーター自体のオーバーヘッドやmallocを通らない確保は含まない。
プロセスのピークworking setとcommitも別の値として保存した。

`estimatedCheckpointMiB` は画像payloadへ既存の非画像状態の計測量を加えた参考値。
新形式の保存オブジェクトを実際に作成した総量やプロセス全体のRAMではない。

## ソースと再実行

OpenZL 0.3.0、Zstandard 1.5.7、LZ4 1.10.0の公式アーカイブをSHA-256固定で使用する。
OpenZL本体のアルゴリズムは変更しない。依存ソース・ライセンスとビルド生成物は `.local/openzl-trial/` に置く。
Zstdの上流makefileが空白を含む作業パスで空archiveを作ったため、公式のsingle-file生成器で
単一スレッド版を作成し、OpenZL側のZstdフォールバックにも同じライブラリをリンクした。
WindowsのGCC一時ファイルのパス制約を避け、コンパイルはpipeと明示したobject出力で行う。

既存の `experiments/dav1d-checkpoint-storage/` を実行済みのWindows/MSYS2 MinGW64環境で:

```powershell
python experiments/openzl-checkpoint/prepare.py
python experiments/openzl-checkpoint/run.py
python experiments/openzl-checkpoint/run.py --extend-native-lz
python experiments/openzl-checkpoint/native_cpu.py
```

元の動画名・ファイルパスや参照画像そのものはレポジトリーへ保存しない。
入力のハッシュ・全生値・コンパイル対象ソース/ライブラリのハッシュは各JSONへ保存した。
`results.json` が標準9方式、`native-lz-results.json` が標準ビルドの独自LZ4方式、
`native-cpu-results.json` がCPU最適化あり13方式。集計検査は `verification.json`。

今回の範囲ではGPU改造を進める根拠になるような容量の優位性は見つかっていない。
CPU版の採用は、既存Zstdの同時再生負荷と比較したiPhone実測で判断する。
