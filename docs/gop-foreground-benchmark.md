# ローカル動画のGOPシーク測定

## 成功条件

エーテルの通常の`NeoPlayerController`で音声付きローカル動画を前面再生し、共通の絶対時刻への送り・戻しを測る。別の復号専用プレイヤーは作らない。元の再生エンジン・チェックポイント・字幕・コメントのグローバル設定は変更しない。測定セッションではチェックポイントを無効にし、字幕・コメントなし・等速・横画面を基準とする。履歴・Annictへの書き込みは行わない。

設定→視聴→GOPシーク測定（ローカル）から、PCで生成した測定計画JSONと動画を「ファイル」でまとめて選ぶ。動画はアプリの領域へコピーされるため空き容量が必要。コピーと初期読み込みの時間はシーク時間に含めない。計画に記録したファイルサイズで対象を照合し、再生時にも長さを確認する。ファイルサイズは暗号学的同一性の証明ではない。実ファイルのパスや番組名を結果へ書かない。

`python scripts/gop-plan.py <動画フォルダー> <出力JSON> --ffprobe <ffprobeの実行ファイル> --ffmpeg <ffmpegの実行ファイル>`で生成する。パケットのキーフラグとPTSから前方キー時刻を記録し、平均FPSも保存する。測定位置・準備位置の周辺±2フレームを32×18の輝度画像として計画へ入れる。キーフラグ自体の正しさはコンテナ・映像データに依存する。私的な動画の解析結果・画像はアプリへ同梱・コミットしない。

## 測定手順と時刻の意味

- 共通の24シーク先を使用。各位置へ約10秒前・10秒後から移動し、1周48測定。方向の先行順を交互にし、周回でも反転する。1〜3周を選べる。動画の順序は開始時にランダム化し、結果の順序として保持する。
- 最初に2測定をウォームアップとして記録するが集計から除く。各測定前の準備用シークも集計しない。準備位置の映像を確認して300ms再生してから、測定シークを通常コントローラーの経路へ渡す。送り戻し距離は再生継続分があるため厳密な10秒にはならず、実際の開始位置を保存する。目的位置は全動画で同じ。
- 操作関数の呼び出しから、目的PTS±2フレーム（最低30ms）以内の映像バッファを確認するまでを`displayMs`とする。エンジンのseek戻りは`engineCompletionMs`として別に記録する。画面の物理的な発光を測る光学試験ではない。
- ソフトウェア経路では表示済みsurfaceのsource PTS、AVPlayer経路では現在item時刻の表示用バッファを確認する。検証方法を各行に記録する。表示時刻未確認の画像は成功や高速サンプルとして集計しない。ポーリング間隔は約16.7msで、フレーム周期も含む測定の時間分解能を考慮する。
- 表示サービスがsource PTSを除去する環境では、シーク後の世代で目的位置が復号された通知を受けたうえで、実際の表示済みバッファと計画の画像を照合する。MAE 9/255以内・相関0.985以上を要求し、開始前の画像でも一致する場合や平坦な画像は曖昧として集計から除く。これは近似画像照合であり、表示タイムスタンプの直接取得とは区別する。結果は`referencePTS`と`displayed-picture-reference`を記録し、キューの時刻を`picturePTS`へ書かない。読み戻しの負荷も測定時間へ含み、その累計を併記する。
- 実キー時刻・キーからの距離、実際の再生経路、画面寸法、温度状態、方向・周回を記録する。通信時間はローカル化で除外するが、ファイルI/O、OS・エンジンキャッシュ、音声同期、描画は含む。
- 手動操作・中断・前面から外れた場合・PiP・再生停止や復旧では中断する。途中結果を保存し、失敗を成功に含めない。準備映像を確認できない場合も測定を続行しない。
- 保存ごとに原子書き込みし、`gop-seek-current.json`と完了済み動画の集約`gop-seek-benchmark.json`を共有できる。中央値・90%点・最遅値・平均と試行数/成功数を全体と方向別に残す。

## 検証範囲

Foundationの試験で計画の検証、キーの前方探索、共通ターゲット、方向の均衡、失敗除外と統計を確認する。両SDKをビルドし、シミュレーターでは既存の音声付きAV1動画を使い、実際の通常プレイヤーでウォームアップ2回・測定6回を行う。目的PTS、エンジン通知との分離、途中/最終JSON、前面再生の画像を確認する。これはiPhone実機の性能値とは扱わない。

初回はUIKitの継承プロパティとの名前衝突を修正。続く実再生試験で、表示済みバッファのCVBuffer添付情報・IOSurface値の両方が失われることを確認した。取得成功と見なす条件を緩めず、表示画像の参照照合を追加して再検証する。画像照合は測定セッション限定で、通常再生には追加しない。

参照画像の縮小はCore Imageに合わせてリニア光で行い、sRGBへ戻して輝度化する。色行列はBT.709を指定する。SDRの未指定バッファの解釈差を扱うため、sRGB/BT.709転送特性の参照を区別して保持する。既存のシミュレーター画像で、ガンマ符号化されたYUVの縮小ではMAE約19・相関約0.96だったものが、対応する色変換ではMAE約6・相関約0.986となることを確認した。照合閾値は変更しない。参照生成・試験だけの修正は、アプリソースと依存の同一性を検証した上でビルド済みバイナリーを再利用する。

表示画像の照合が成功してから、別の準備シークでenqueue observerの最新時刻が目的位置を通り過ぎ、測定がタイムアウトすることを確認した。測定中だけ目的位置の復号時刻・世代を1件保持し、main-loopのポーリングで取りこぼさないようにした。保持した時刻だけでは表示成功とせず、引き続き表示済み画像の一致が必要。通常再生ではこの保持を有効にしない。

## 確認済み成果物

- アプリソース`20605c0`、ビルド355、Actions run `42365991152`は成功。
- device/simulator両SDKのビルド・FFmpeg import isolation、モデル19件を確認。CI補助スクリプトはローカル27件成功。
- 音声付きAV1の通常プレイヤーで、ウォームアップ2回と測定6回（送り3・戻し3）を完了。全8回が`displayed-picture-reference`で検証済み。走行中の映像、部分/最終JSON、集計を確認。
- 配布IPAのアーティファクトdigest・IPA SHA-256・ソースcommit・CFBundleVersionを照合した。別の変更へ同じ結果を流用していない。
- この結果は機能検証。実機でのGOP別性能比較は配布版で測定する。画像読み戻しの負荷は各行の`referenceReadbackMs`に残り、シミュレーターの値をiPhoneの性能値として扱わない。

## Windowsのドラッグ＆ドロップ作成ツール

`scripts/GOP測定JSON作成.cmd`へ動画・フォルダーをドロップすると、`gop_drop.py`が全動画をまとめたschema 2 JSONを先頭の動画と同じフォルダーへ出力する。Python標準ライブラリとffprobeだけを使用し、参照画像の生成・映像復号は行わない。元の`gop-plan.py`は同一時刻・参照画像付きの比較用として維持する。新形式は修正版アプリが必要で、ビルド355には渡せない。

新ツールは乱数を使わず、均等な8つの時間帯から別々の実GOP区間を選び、各区間の近・中央・遠を映像パケットPTSから選択する。近・遠にはアプリの±2フレーム（最低30ms）の判定幅と、さらに1フレーム分の余裕を取り、次のキーに判定範囲が入ることを避ける。3つの判定範囲が重なる短い区間は対象外。各区間の実際の長さはJSONへ記録し、公称GOP長へ置き換えない。8区間×3位置×2方向＝48回で、現行アプリのウォームアップ2回・周回設定を使用する。

各GOP版で絶対時刻は異なるため、従来の同時刻比較とは分ける。`profiles[].targets/points`に各動画の測定位置・区分・前後キー・キーからの距離・区間内割合を保持する。アプリは動画別の位置を使い、結果にも`group/section/nextKeySeconds`を保存する。`summaryByGroup`に近・中央・遠の集計を追加する。従来のschema 1共通位置・参照画像付き計画の読み込みも維持する。

動画・パスをシェルコマンドに組み立てずffprobeへ引数配列で渡す。デスクトップショートカットはPythonを直接起動する。複数入力の重複を除き、フォルダーは直下のみ対象とする。生成済みファイルは上書きせず連番を付ける。JSONの4MiB上限・区間数不足・12本上限・同サイズの識別不能を確認し、一部が失敗した場合は部分的な統合JSONを出力しない。

## 連続測定と軽量計画

動画ごとにプレイヤーを閉じて作り直す代わりに、同じ前面コントローラーとエンジンで入力を置き換える。最初の測定開始は`viewDidAppear`後とし、後続入力ごとの画面回転・音声セッション終了を避ける。入力の準備状態・表示時刻の証拠・失敗状態を切り替え時に初期化する。ローカル測定の失敗は通常の通信再接続ループへ入れず、中断理由と状態を結果へ保存する。

参照画像のない計画は表示タイムスタンプを取得できる経路のみで測る。時刻がない場合に復号通知を表示完了と見なすことはせず、明示的な理由で中断する。旧計画の画像照合は残すが、通常の軽量計画では画像読み戻しも行わない。

成功条件はモデル26項目、JSONツール14項目、両SDKビルド、既存のAV1画像照合試験に加え、公開H.264素材3入力の連続測定。schema 2の実際の選択処理を通し、動画別に異なる測定位置、表示時刻、近・中央・遠の集計、1回だけの画面提示・3回の入力読み込み、参照画像なしを確認する。iPhone実機のAV1での連続動作・性能の最終確認は別途必要。

初回の3入力はすべて完了し、表示済みsurfaceのsource PTSで全24回を確認できたが、試験側がAVPlayerの経路名だけを要求していたため失敗した。表示時刻付きソフトウェア経路も元の測定契約に適合するため、その検証名を受理する。キューの時刻やエンジン完了だけでの成功は引き続き受理しない。アプリの変更は不要で、同じバイナリーの再利用で再検証する。

再利用試験では、3本目の最初の準備シークで表示時刻の許容範囲を取り逃がした。1枚目が表示された直後にシークを開始していたため、開始前の準備条件を「3枚以上・0.25秒以上の表示時刻の進行・再生中・バッファリングなし」に変更する。入力間で復号フレームの収集器と表示世代を更新し、古い入力のコールバックを新しい入力の証拠に混ぜない。測定許容幅とシーク時間の定義は維持する。再現したMP4→1080p MKV→小サイズMKVの順序をシミュレーター試験で固定する（実機で選択した動画の順序は従来通りランダム）。

## 軽量・連続測定版の確認結果
