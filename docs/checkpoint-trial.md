# AV1 状態復元診断

設定 → アプリ設定 → 再生エンジンで「診断用：AV1状態復元」を選び、
エンコード済み AV1 の PLAY を開き、「診断を開始」を押す。
以前と同じ長い GOP の動画を使う。対象は 1920×1080 以下。
通常の視聴経路、TS、STREAMING、コメント、PiP、視聴履歴は変更しない。
以前の「AV1復号比較」も別項目として残す。

## 測定条件（schema 3）

先頭の実キーフレームから次のキーフレームの約 1 秒後までの圧縮パケットを取得する。
準備上限は96MiB・3,000パケット・65メディア秒・90秒。一時MP4はcodec copyで作り、
終了時に削除する。通信・デマルチプレクス・MP4作成は復号タイマーに含めない。

目的位置は最初の GOP の90%。下表を1・2・4・6スレッドで測る（合計16条件）。

| 保存方式 | 目的位置までの距離 |
| --- | --- |
| 元の参照画像を保持 | 約6秒 |
| 10bit無損失パック | 約6秒・2秒・0.25秒 |

短いGOPでは距離を縮め、実際のパケット境界・目的画像時刻も記録する。
フレーム並列度はdav1dの自動設定で1・2・2・3。処理グループ間でスレッド順を変える。
途中フレームのスキップは行わない。入力ごとの全ドレインを避け、通常の並列投入を保つ。
保存前には全出力を受け取り、ワーカーの待機を確認する。スレッドやmutexの保存ではない。

各条件で保存5回・復元5回を測る。`restoredMs` は保存状態の復元開始から目的画像の取得まで、
`restoreOnlyMs` は復元のみ、`repeatedSaveMs` は保存のみ、`drainBeforeSaveMs` は保存前の
残り出力待ち。通常復号と全Y/U/V画素・時刻・出力数を比較する。全後続区間の照合は2回、
別途、真の次キーフレームを越えてから戻す5回すべてで目的画像を全画素比較する。
いずれも画素比較は速度計測の外。重い先頭からの基準復号を毎回やり直す旧測定は外した。
以前の単一スレッド測定とは測定方法も異なるため、今回の同じ動画・条件間で比較する。

パック方式は10bitの有効画素を16bit格納から10bit格納へ無損失で詰め、余白も完全保存する。
8bitは画素のビット圧縮をしない。元画像への隠れた参照がないこと、復元後のアロケーション
全体（余白含む）の一致も2回確認する。空・未処理出力ありの保存、別所有者への復元、
状態なしの非キーフレーム再開を拒否することも確認する。

## 結果と制限

「診断結果を共有」で `checkpoint-benchmark.json` を共有する。
16条件すべて成功なら `status=complete`、不一致・未対応・上限到達は `partial`。
準備失敗は `failed`。各条件終了時にも結果を保存し、中断時は完了した行を残す。
ソースURL・タイトル・画像・認証情報は結果に入れない。

各行の `status=0` が成功。1001入力、1002境界、1003不一致、1004目的画像/後続キーなし、
1005保持上限、1006中断、1007条件ごとの180秒上限、1008復号失敗（`decoderError`）。
`failureStage` は1入力、2準備復号、3保存、4全区間照合、5復元測定、6拒否検査。
成功時は0。復号器・画像・保持状態・借用入力は成功/失敗/中断時に解放する。
閉じる、バックグラウンド移動、メモリー警告で中断する。

`retainedBytes` は1地点が保持するデータ量で、復号器の作業領域やプロセス全体とは異なる。
`sampledFootprintBytes` は5回の復元時、`processFootprintAfterBytes` は各条件の後、
`processFootprintAfterInputReleaseBytes` は全条件と圧縮入力解放後のプロセスphys_footprint。
アロケーターのキャッシュを含み、増加だけでリークとは判断しない。標本最大は厳密なピーク
ではない。開始/終了時のthermalStateも記録するが、消費電力は測定していない。

この診断は同一プロセス・同一復号器・既定アロケーター限定。HDRメタデータ等の境界は未対応。
画像を復号して取得するまでの試験で、音声同期・画面表示込みのシーク速度ではない。
複数地点を通常プレイヤーへ保持する機能は今回追加しない。

## ビルドと分離

`scripts/build-checkpoint.py` はdav1d 1.5.4の
`54706fc6bc0cdecab7e9593974a4039cc038fca7` を固定する。
`vendor/checkpoint/` にPCで確認した並列・パック方式を収録し、アプリとの境界は
`NeoCheckpointLab.h` の単純なC型だけとする。PC実験は `experiments/dav1d-mt-checkpoint/`。
全public dav1d APIを `neo_lab_` 接頭辞へ変更し、Apple側ではシンボルを非公開にする。
既存の動的AetherLibdav1dとは分離。ライセンス・固定ソース情報・追加ソースをIPAへ収録する。

Actionsの `checkpoint-trial` はdevice/simulatorビルドと診断画面の8bit/10bit各16条件に絞る。
シミュレーター成功はiPhoneの速度・熱・電力を保証しない。実機結果で次の採用判断を行う。

## ビルド269の確認

ソース `050477c45f17c5d9a56888abb02d765c1c1825de`、
[Actions 40172537801](https://github.com/nyanz00/NeoEPGStation-iOS/actions/runs/40172537801)
で device / simulator のビルドと診断画面の試験に成功。

各条件の全画素照合を伴う 5 回復元・5 回の一時保存解放・入力/所有者の拒否検査、
phys_footprint と共有用 JSON の出力を確認した。
通常経路の FFmpeg インポート先も Aether フレームワークへ結び付いている。

IPA: `NeoEPGStation-build269.ipa`、SHA-256:
`d2b041dd6d661fac22081dd6612760c71991d8527729a0bf3fd748d3a89111fa`。
GitHub が記録するファイルの digest、ZIP CRC、埋め込みビルド番号、
収録した checkpoint のソース/ライセンスと Aether のパッチレシピを照合済み。
iPhone での速度・熱・電力の測定は未実施であり、シミュレーター試験と区別する。
