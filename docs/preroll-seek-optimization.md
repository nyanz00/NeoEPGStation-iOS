# キャッシュ内シークの映像再開時間

デコーダーの選択成功と、戻し送りの待ち時間改善は別に検証する。
AV1ハードウェア利用済みでも、目的位置より前の復号と出力管理は残る。
機能試験の成功だけを、実機での速度改善の証明には使わない。

## パッチ適用版4

HEVCとAV1の処理量を減らす。画像出力を省くことと、復号への投入自体を
省くことは分ける。OSのOnlyTheseFramesが非対応でも後者を利用できる。

- HEVCは全VCL NALが有効なlayer 0の_Nで、各スライスのアクティブSPSの
  最高TemporalIdに一致する場合だけ省略する。_Nは同一時間階層での非参照で
  あり、低い階層の_Nを一律に削除しない。POC/SEI/DPBの時刻情報は維持する。
- AV1は参照スロットを更新しない表示INTERフレームと、既知の非KEY参照の
  show-existingだけを対象とする。show-existing KEYは全参照スロットを
  更新するため残す。参照画像の種類だけを通常再生時から追跡し、flushと
  sequence変更でリセットする。未知の参照、隠れた画像、複数画像のTU、
  メタデータ更新、frame ID、decoder model、複数operating pointは省略しない。
- show-existingの後にはframe_typeがない。AV1の出力順情報で、その後の
  paddingをKEYと誤読してDPBをflushしない。
- CoreMediaのサンプルdurationをVLCのマイクロ秒単位から変換し、未知DTSを
  kCMTimeInvalidにする。従来AV1だけに適用していた補正をHEVC等にも適用する。

判定部分は `vendor/vlckit/neo_preroll.h`。AV1の参照情報は
[AV1仕様のrefresh_frame_flags / show_existing_frame](https://aomediacodec.github.io/av1-spec/)
に従い、HEVCはH.265のsub-layer non-reference pictureの制約に従う。
不明な場合は元の復号へ通し、目的位置やキーフレームを丸めない。

`scripts/preroll-reference-test.py` は実際のCコードをコンパイルし、FFmpegで
解析した合成AV1 8/10bit、HEVC 10bitから30秒以前の対象だけを取り除く。
元と除去後の復号画像のうち30秒以降の42秒・1008枚がすべて同一であることを要求する。
隠れたフレーム等を含む元のビットストリームで参照の保持を検証する。
手元の結果はそれぞれ358 / 358 / 359フレームを省略、各1008枚一致。
この試験をiPhone実機での速度向上の証明には使わない。
FFmpegを使う全画像比較は手元で実施済み。CI事前検証は同じCコードの
コンパイルと拒否条件を `--guards-only` で確認し、外部のFFmpeg取得を
iOSビルドの前提にしない。guards-onlyの成功を全画像一致とは報告しない。

`--compare-hevc` は同一バイナリ・同一HEVC 10bit・同一8シーク先の比較。
baselineもpreroll画像出力省略は有効（適用版3相当）で、新しいHEVC/AV1の
復号省略だけを `NEO_EPG_REFERENCE_BASELINE=1` で無効にする。
通常配布アプリでは常に有効。H.264の既存省略とAV1の非対応機種での
dav1dへの切り替えも退行確認する。実機の速度改善は別途実測が必要。

最初の適用版4アプリ試験では、H.264 MKVの継続再生判定のみ失敗した。
診断sampleの約1秒間に出力sampleは14枚届き時計も進行していたが、遅延更新される
libVLCのdecodedVideo増分は8枚だった。継続判定は実際の出力sampleの
増分が10枚を超えることと時計の進行で行い、前後の値も結果に保存する。
シーク位置・停止・音声の条件は維持する。この修正でライブラリは変更せず、
同一性を検証した完成済みの実機／シミュレーター用成果物を再利用する。

Build 236ではH.264の192項目が成功した。続くHEVC 10bitではシミュレーターが
VideoToolboxを使わずavcodecを選び、48項目の再生検査は成功したが、
preroll計測イベントがなく速度検査が停止した。同じアプリの再検証では
実際のdecoderを結果に残し、この環境でのHEVCは再生の退行確認に限る。
VideoToolboxの速度が測れた場合だけ20%以上の短縮を要求する。
ソフトウェアへ切り替わった結果を、HEVCの修正経路の検証や速度向上として
扱わない。AV1も同じく、シミュレーターでの退行確認と実機の速度を区別する。

## パッチ適用版3

VLCが明示的にPREROLLとした、PTSがあるプログレッシブフレームについて、
VideoToolboxへ `kVTDecodeFrame_DoNotOutputFrame` を渡す。
参照画像の復号とPOC・DPB・タイミングの情報は維持し、VLCの出力画像の作成と
CVPixelBufferの取り付けを省く。フレームの出力順を無視した高速シークには変えない。
未確定の時刻、フィールド、通常再生の画像にはこの省略を適用しない。

画像出力しない前処理だけ、最大16フレームの非同期キューを使う。
表示中の画像の解放を待つ通常のpacer制限に依存させず、無制限にも投入しない。
通常の画像出力とメモリー制限は維持する。
出力省略時のNULL画像を故障扱いせず、VTがヒントを無視して画像を返した場合も
VLC画像には包まず破棄する。

出力省略ではDecodeFrameから戻る前にcallbackが来る場合も扱う。
キュー投入数を呼出前に計上し、callback所有のframe_infoを呼出後に読み直さない。
同期エラー時は投入数を戻してframe_infoを解放する。
既存のflushは古いcallbackの完了を待ち、前処理の統計をリセットする。

画像出力省略だけの適用版2は、1080p MKVの同一バイナリ比較で中央値が
無効約1.64秒／有効約1.73秒となり、速度改善を確認できなかった。
前処理のキュー待ちは約1msで、画像管理より復号自体が支配的だった。
この実験を成功とは扱わず、参照に不要なフレームの復号省略へ変更した。

H.264は全VCL NALが非参照スライスの前処理フレームに限り、VTへ投入しない。
既存パーサーのSPS/PPS/SEI/POC更新と、出力順・時刻のDPB情報は維持する。
AV1は参照スロットの判断をVTに任せ、前処理でOnlyTheseFrames/NonDroppableFramesを
要求し、通常フレームを投入する前にAllFramesへ戻す。
非対応なら通常の復号を続け、要求の成否はvlc.prerollFilterへ残す。
通常出力への復元が失敗した場合は、フレームを欠落させず既存のソフトウェアへの
切り替えを使う。VLCDEC_RELOADでは呼出側が保持する入力blockを解放しない。

1080p試験で露出した停止後の音声カウンター増加は、ミュートした準備中の統計が
Paused通知後に集計されるためだった。VLCの統計更新間隔は既定250msなので、
試験では2更新間隔後のカウンターを起点に、さらに1秒間不変であることを要求する。
停止位置とPaused状態の検査は最初の停止通知を起点とし、実装の待ち時間は増やさない。

## 比較方法

`encoded-seek` は同じシミュレーターアプリで有効・無効を切り替え、
同じ1080p・24fps・24秒間隔のGOP・3 Bフレーム設定のH.264 MKV/MP4を再生する。
同一の8シーク先、先に取得した同じキャッシュを使い、MKVとMP4で実行順を反転する。
正確な位置、映像進行、再取得・入力再作成なし、停止中の復旧を各48項目で確認する。
有効時にnoOutputが実際に増え、picturesが0になることも要求する。
`preroll-comparison.json` には各シークの映像再開時間と、前処理時間・画像数を残す。

同じscopeでAV1 8/10bitのMKV/MP4も確認する。
AV1非対応シミュレーターはdav1dの退行確認であり、実機AV1の短縮量の確認には使わない。
実機の `vlc.prerollReady` は出力省略数、画像作成数、キュー待ち、前処理時間を記録する。
シークの受付callbackと、映像が再開した `seek.videoResume` を区別する。

1008枚がすべて元の復号画像と一致した。これは参照関係の検証であり、
